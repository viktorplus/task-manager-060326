## Как проверялось

В файле есть операции записи (`create`, `update`, `bulk_update`, `tag.add`), поэтому **на рабочей базе код не выполнялся**. Оба прогона сделаны на копиях SQLite через отдельный модуль настроек; контрольная сумма `db.sqlite3` после проверки не изменилась.

1. **Чистая база.** Пустая база после `migrate`, задания выполнены по порядку. Проверяет, воссоздаёт ли файл данные с нуля.
2. **Копия рабочей базы.** Каждое задание выполнено в отдельной транзакции с откатом. Показывает вывод на ваших данных и то, какие строки `Task` задание **изменило бы**.

Кроме того, на рабочей базе выполнены только запросы на чтение: проверка паролей, количество задач для задания 24, теги. Выводы ниже основаны на фактическом выводе этих прогонов.

## Замечания по заданиям

### Задание 1 — создание тегов ✅

5 тегов (`Backend`, `Frontend`, `Q&A`, `Design`, `Devops`) на чистой базе создаются. При повторном запуске падает с `IntegrityError: UNIQUE constraint failed: core_tag.name` — это ожидаемо, если раскомментировать код второй раз. Все строки пишут в одну и ту же переменную `new_tag`.

### Задание 2 — проекты и файлы ⚠️

- Проекты и записи `ProjectFile` создаются, связь `files.add(...)` работает.
- В `FileField` передана просто строка `"projects/1/file.txt"`: в базе появляется путь, а **самого файла на диске нет**. `MEDIA_ROOT` в настройках не задан, папки `media` нет.
- При повторном запуске ошибки не будет, и это хуже: появятся **дубликаты**. Уникальна только пара `title + description`, а описание существующего `Project1` уже изменено на `'Description1'`. Второй `Project1` создастся без ошибки, и потом `Project.objects.get(title="Project1")` из задания 5 упадёт с `MultipleObjectsReturned`.

### Задание 3 — пользователи ⚠️

- `User.objects.create(username=..., password="password")` сохраняет пароль **как есть, без хеширования**. Проверено на рабочей базе: у всех пяти пользователей `check_password("password")` возвращает `False`, то есть войти под ними нельзя. Для создания пользователя с паролем нужен `User.objects.create_user(...)`.
- Код проверки (`filter(username__in=...)`, `values`, `count`) работает: `Количество: 5`.
- У пользователей не указан `email`, поэтому в заданиях 13 и 15 строка «Email» пустая.

### Задание 4 — нет в файле

Нумерация в файле идёт 1, 2, 3, 5. Условие задания 4 неизвестно, оценить его нельзя.

### Задание 5 — создание задач ⚠️

- Создаются 3 задачи: две в `Project1` и одна в `Project2`. Условие — «по одной-две для каждого тега», но для тегов `Q&A` и `Design` задач нет.
- В первых двух задачах `due_date=date(2024, 6, 30)` — это «наивная» дата в `DateTimeField`. Django выдаёт предупреждение `RuntimeWarning: DateTimeField Task.due_date received a naive datetime`. В третьей задаче правильно используется `timezone.make_aware(...)`, то есть подход в файле непоследовательный.
- Пункт 4 («убедитесь, что данные сохранены») в коде не отражён.
- Задачи называются «... Task 2», а «Backend Task 1», от которой зависит задание 6, в файле не создаётся.

### Задание 16 — приоритет задач на следующий месяц ⚠️

- Следующий месяц вычисляется правильно, в том числе для декабря.

- Закомментированный вариант с `F('created_date__month')` ссылается на несуществующее поле `created_date` (в модели оно называется `created_at`) и работать не будет.

### Задание 19 — задачи по тегу ⚠️

- По условию тег — «**Q&A**», а в коде `tag__name__icontains="Backend"`, рядом стоит пометка `###???`. На рабочей базе у тега `Q&A` нет ни одной задачи (проверено), видимо, поэтому его заменили. Для «конкретного тэга» точнее подходит `tag__name="Q&A"` без `icontains`.

### Задание 20 — проекты с файлами за неделю ✅

### Задание 22 — `due_date` на +3 дня через `bulk_update` ✅

### Задание 23 — проекты по дате и числу файлов ❌

- **Падает** на обеих базах: `AttributeError: property 'file_count' of 'Project' object has no setter`. Имя аннотации `file_count` совпадает со свойством `Project.file_count` в модели. Нужно другое имя аннотации, например `files_total`.
- `timezone.datetime(...)` — это не часть API `django.utils.timezone`, а модуль `datetime`, который просто импортирован внутри него. `.astimezone()` для «наивной» даты берёт часовой пояс **операционной системы**, а не `TIME_ZONE` из Django. Надёжнее `timezone.make_aware(datetime(2020, 7, 7))`.
- Порог файлов — 1 вместо 3 из условия. Видимо, это подгонка под данные; её стоит пояснить комментарием.

### Задание 24 — срочные задачи до конца месяца ❌

- Это единственный незакомментированный код в файле, но запрос **находит 0 задач**. В фильтре стоят `"High"` и `"Low"` (подписи), а в базе хранятся значения `"high"` и `"low"`. На рабочей базе с правильными значениями нашлась бы задача «DevOps Task 2».
- По условию нужен приоритет «Critical» или «Urgent». Ближайший аналог в модели — только `high`; `low` — это противоположность срочности.
- `end_of_month` сохраняет текущее время суток, поэтому задачи со сроком в последний день месяца, но позже этого времени, не попадут в выборку. Нижней границы нет, поэтому попадают и давно просроченные задачи (например, со сроком в 2024 году).
- Результат никак не используется и не выводится. `import calendar` стоит в середине файла.
